# Verified Presence 파트너 핸드오프 기술명세서

작성일: 2026-06-29  
서비스명: Verified Presence  
기존 프로젝트명/배포명: verified-ai-cast  
운영 URL: https://verified-ai-cast.vercel.app

## 1. 이 문서의 목적

이 문서는 공동파트너와 파트너의 AI가 지금까지 구현된 내용을 빠르게 파악하고 다음 작업을 이어갈 수 있도록 만든 핸드오프 문서입니다.

특히 현재 가장 중요한 문제는 “사용자가 처음 들어왔을 때 무엇을 해야 하는지 막막하다”는 점입니다. 따라서 이 문서는 단순 기능 목록이 아니라 판매자와 구매자 UX 플로우를 명확히 분리하고, 다음 개발자가 어떤 구조로 개선해야 하는지까지 포함합니다.

## 2. 제품의 핵심 정의

Verified Presence는 AI 에셋 생성 툴이 아닙니다.

핵심은 인증입니다. 판매자, 구매자, 브랜드, 제작사가 고가치 디지털 에셋을 거래하거나 영상/광고/콘텐츠에 사용할 때 다음 질문에 답하는 신뢰 레이어입니다.

- 이 에셋은 진짜인가?
- 이 판매자는 이 에셋을 판매하거나 승인할 권한이 있는가?
- 이 사용 범위는 실제 권리자가 승인한 범위인가?
- 이 URL 또는 콘텐츠는 승인된 배포본인가?
- 문제가 생기면 인증 상태를 추적, 정정, 취소할 수 있는가?

현재 이름은 Verified Presence로 정리되어 있습니다. “AI Cast”는 배우/인물 에셋에 특화된 하위 프로그램 이름으로 남길 수 있지만, 제품 전체를 대표하기에는 좁습니다. 제품은 배우뿐 아니라 브랜드 제품, 명품, 캐릭터, IP, 광고용 디지털 에셋까지 다뤄야 합니다.

## 5. 핵심 역할 정의

### 5.1 판매자

판매자는 에셋을 등록하고, 본인이 그 에셋을 판매하거나 승인할 권한이 있음을 증명하는 사람 또는 조직입니다.

예시:

- 배우 본인
- 배우의 에이전시
- 브랜드 담당자
- 브랜드 라이선스 대행사
- IP 권리자
- 제품 배치 권한을 가진 마케팅 담당자

판매자의 핵심 질문:

> 내가 이 에셋을 판매하거나 승인할 권한이 있음을 어떻게 증명하고, 어떤 조건으로 허용할 것인가?

판매자 UX는 “증명 제출”과 “조건 통제”가 중심이어야 합니다.

### 5.2 구매자

구매자는 특정 에셋을 콘텐츠, 광고, 영상, 캠페인, AI 제작물, 제품 배치 등에 사용하려는 사람 또는 조직입니다.

예시:

- 제작사
- 광고 대행사
- 브랜드 캠페인 팀
- AI 영상 스튜디오
- 콘텐츠 플랫폼
- 커머스/리테일 팀

구매자의 핵심 질문:

> 이 판매자, 에셋, 인증서, URL을 믿고 돈을 내거나 공개해도 되는가?

구매자 UX는 “신뢰 판단”과 “다음 행동”이 중심이어야 합니다.

### 5.3 브랜드/VIP 기업

브랜드는 제품 배치 또는 명품/정품 인증이 중요한 에셋 발행자입니다.

예시:

- Gucci, Prada 같은 명품 브랜드
- 전자제품 브랜드
- 자동차 브랜드
- 뷰티/패션 브랜드

브랜드 UX는 일반 판매자와 비슷하지만, 사람 에셋이 아니라 제품/브랜드 에셋을 등록하고 “정품 URL 인증”을 받는 흐름이 더 중요합니다.

### 5.4 검수자

검수자는 제출된 증거, 권한, 사용 범위, URL, 최종 콘텐츠를 검토해 인증서를 승인/반려/취소하는 내부 또는 외부 검수 담당자입니다.

검수자 UX는 체크리스트, 증거 비교, 리스크 판단, 결정 기록이 중심이어야 합니다.

### 5.5 운영자/창업자

운영자는 실제 상용화 전까지 수동으로 처리해야 하는 법률, 결제, 심사, 고객응대, 파트너 영업, 투자유치 업무를 담당합니다.

운영자 화면은 실제 사용자에게 보이면 안 되는 피칭/내부 섹션으로 유지해야 합니다.

## 6. 현재 가장 큰 UX 문제

현재 `/operations`에 역할별 시작 카드가 있지만, 사용자가 카드를 누른 뒤에도 다음 화면이 명확한 역할별 여정으로 이어지지 않습니다.

주요 문제는 다음과 같습니다.

- 판매자와 구매자가 같은 콘솔을 공유하는 느낌이 남아 있음
- “나는 무엇부터 해야 하지?”에 대한 첫 행동이 약함
- 판매자는 에셋 금고, 권한 증빙, 판매 조건 설정 흐름이 부족함
- 구매자는 인증서 조회 후 “그래서 결제/요청/확인 중 무엇을 해야 하는지”가 부족함
- 브랜드 제품 에셋 등록은 있지만 거래/인증서/URL 승인 흐름과 충분히 연결되어 있지 않음
- 거래방, 딜룸, 요청/승인 상태가 실제 페이지 구조로 존재하지 않음
- 가상 시나리오와 실제 워크스페이스가 분리되어 있어 데모 흐름이 끊김
- 로그인 후 역할에 따라 메뉴와 CTA가 바뀌는 구조가 아직 없음
- 백엔드 저장소가 없어 사용자가 다시 들어오면 이어서 작업하는 제품 경험이 아님

따라서 다음 단계는 기능을 더 많이 추가하는 것보다 “역할별 시작점과 다음 행동”을 선명하게 만드는 것이 우선입니다.

## 7. 목표 UX 구조

### 7.1 공통 시작 구조

사용자가 들어오면 다음 질문에 바로 답할 수 있어야 합니다.

- 나는 에셋을 등록/판매하려는 사람인가?
- 나는 에셋을 구매/검증하려는 사람인가?
- 나는 브랜드 제품을 등록하려는 기업인가?
- 나는 제출물을 검수해야 하는 사람인가?

권장 구조:

- `/start` 또는 현재 `/operations`를 명확한 시작 허브로 개선
- 역할 선택을 세션 또는 프로필에 저장
- 선택한 역할에 따라 메뉴, CTA, 빈 상태 문구, 다음 단계가 바뀌게 구성

사용자 친화적 표현:

- “판매자 콘솔”보다 “내 에셋 등록하기”
- “구매자 콘솔”보다 “인증된 에셋 확인하기”
- “Submission”보다 “검토 요청”
- “Review”보다 “인증 심사”
- “Certificate”보다 “인증서”
- “Ledger”보다 “정산 내역” 또는 “거래 기록”

## 8. 판매자 UX 플로우

판매자 플로우는 “내 에셋을 안전하게 등록하고, 구매자가 믿고 사용할 수 있게 만드는 과정”입니다.

### 8.1 판매자 첫 화면

판매자가 처음 들어왔을 때 보여야 할 핵심 문구:

> 판매할 에셋을 등록하고, 권한 증빙을 제출한 뒤, 구매자가 사용할 수 있는 조건을 설정하세요.

첫 화면의 주요 CTA:

- 에셋 등록하기
- 권한 증빙 제출하기
- 사용 조건 설정하기
- 구매 요청 확인하기

### 8.2 판매자 단계

1. 판매자 계정/조직 생성
   - Google 로그인
   - 개인/회사 구분
   - 담당자 정보
   - 법적 권한 확인 상태

2. 에셋 등록
   - 에셋 유형: 인물, 제품, 브랜드, 캐릭터, 기타 IP
   - 에셋명
   - 소유자/권리자
   - 대표 이미지 또는 레퍼런스
   - 시장/국가

3. 권한 증빙 제출
   - 신분/회사 증빙
   - 에이전시 계약서
   - 브랜드 위임장
   - 제품 정품 증빙
   - 원본 파일 또는 출처 자료

4. 사용 조건 설정
   - 허용 채널
   - 허용 국가
   - 사용 기간
   - 금지 사용처
   - 사전 검수 필요 여부
   - 가격 또는 협의 방식

5. 구매자 요청 검토
   - 구매자 정보
   - 사용 목적
   - 콘텐츠 유형
   - 게시 URL
   - 예산/결제 조건

6. 승인/수정 요청/거절
   - 승인하면 인증서 발급 흐름으로 이동
   - 수정 요청 시 구매자에게 필요한 변경사항 전달
   - 거절 시 사유 기록

7. 인증서/정산 확인
   - 승인된 사용 범위
   - 승인된 URL
   - 결제/정산 상태
   - 인증 취소 또는 분쟁 상태

### 8.3 판매자 화면에 반드시 필요한 빈 상태

판매자에게 아무 데이터가 없을 때는 “비어 있음”만 보여주면 안 됩니다.

필수 빈 상태:

- 아직 등록된 에셋이 없습니다. 첫 에셋을 등록하세요.
- 아직 권한 증빙이 제출되지 않았습니다. 구매자에게 신뢰를 주려면 권한 증빙이 필요합니다.
- 아직 구매 요청이 없습니다. 인증 가능한 공개 링크를 공유하거나 샘플 거래를 만들어보세요.

## 9. 구매자 UX 플로우

구매자 플로우는 “이 에셋을 믿고 사용해도 되는지 확인하고, 필요하면 사용 요청을 보내는 과정”입니다.

### 9.1 구매자 첫 화면

구매자가 처음 들어왔을 때 보여야 할 핵심 문구:

> 인증서, 에셋 URL, 판매자 정보를 입력하면 사용 가능 여부와 다음 단계를 확인할 수 있습니다.

첫 화면의 주요 CTA:

- 인증서 확인하기
- 에셋 URL 검사하기
- 사용 요청 보내기
- 샘플 거래 체험하기

### 9.2 구매자 단계

1. 인증 대상 입력
   - 인증서 ID
   - 판매자가 보낸 URL
   - 에셋명 또는 프로젝트명
   - 공개 콘텐츠 URL

2. 신뢰 요약 확인
   - 인증 상태: 유효, 만료, 취소, 검토 중
   - 판매자 신원 확인 여부
   - 권한 증빙 확인 여부
   - 승인된 사용 범위
   - 승인된 게시 URL
   - 위험 신호

3. 사용 목적 입력
   - 캠페인/콘텐츠명
   - 사용 채널
   - 국가/시장
   - 기간
   - 예산
   - 게시 예정 URL

4. 판매자에게 사용 요청
   - 요청 내용이 딜룸으로 생성됨
   - 판매자와 검수자가 같은 요청을 기준으로 판단

5. 결제 또는 결제 예약
   - 현재 수익 없는 단계에서는 실제 결제보다 수동 인보이스/테스트 결제 우선
   - 결제는 권한과 사용 범위가 확정된 뒤 진행

6. 인증서 수령
   - 인증서 ID
   - 승인된 URL
   - 사용 가능 범위
   - 만료일
   - 취소/분쟁 정책

7. 사후 확인
   - 공개 후 URL이 승인 범위와 일치하는지 확인
   - 인증 상태 변경 알림

### 9.3 구매자 화면에 반드시 필요한 빈 상태

- 확인할 인증서가 있나요? 인증서 ID나 URL을 입력하세요.
- 아직 사용 요청을 보내지 않았습니다. 인증된 에셋을 사용하려면 요청을 생성하세요.
- 이 인증서는 유효하지만 현재 입력한 URL은 승인 목록에 없습니다.

## 12. 딜룸 개념

현재 가장 필요한 신규 UX 단위는 딜룸입니다.

딜룸은 판매자와 구매자가 같은 거래를 서로 다른 관점으로 보는 공간입니다.

판매자에게는:

- 누가 내 에셋을 쓰려 하는가?
- 어디에 쓰려 하는가?
- 조건에 맞는가?
- 승인할 것인가?

구매자에게는:

- 이 에셋은 진짜인가?
- 이 판매자는 권한이 있는가?
- 내가 쓰려는 범위가 승인 가능한가?
- 결제/공개 전에 무엇이 남았는가?

검수자에게는:

- 증거가 충분한가?
- 요청 범위가 정책과 일치하는가?
- 최종 URL이 승인 대상인가?
- 인증서를 발급해도 되는가?

권장 라우트:

- `/deals/deal-01`
- `/ko/deals/deal-01`
- `/seller/assets`
- `/ko/seller/assets`
- `/buyer/verify`
- `/ko/buyer/verify`
- `/brand/products`
- `/ko/brand/products`

현재는 이런 명확한 라우트가 부족합니다. 다음 개발 단계에서 우선 구현해야 합니다.

## 15. 다음 개발 우선순위

### 15.1 1순위: 시작 경험 개선

현재 막막함을 해결하기 위해 가장 먼저 해야 합니다.

작업:

- `/operations`를 역할 선택 허브가 아니라 실제 시작 화면으로 재구성
- 판매자, 구매자, 브랜드, 검수자 각각 “다음으로 할 일 1개”를 명확히 표시
- 샘플 데이터로 바로 체험하는 버튼 제공
- 선택한 역할에 따라 다음 페이지가 다르게 열리도록 구성

완료 기준:

- 처음 들어온 사용자가 10초 안에 자기 역할을 선택할 수 있음
- 각 역할 첫 화면에 “지금 해야 할 일”이 한 문장으로 보임
- 빈 상태에서도 다음 행동 버튼이 보임

### 15.2 2순위: 딜룸 추가

작업:

- 샘플 딜룸 상세 페이지 추가
- 같은 딜룸을 판매자/구매자/검수자 관점으로 볼 수 있게 구성
- 현재 단계, 남은 작업, 누가 해야 하는지 표시

완료 기준:

- 판매자는 승인/수정 요청/거절 액션을 볼 수 있음
- 구매자는 신뢰 상태와 결제 전 남은 작업을 볼 수 있음
- 검수자는 증빙 체크리스트와 결정 버튼을 볼 수 있음

### 15.3 3순위: 판매자 에셋 금고

작업:

- 판매자 전용 에셋 목록
- 에셋 등록 상태
- 권한 증빙 상태
- 사용 조건 상태
- 구매 요청 상태

완료 기준:

- 판매자가 “내가 무엇을 팔 수 있는지” 한 화면에서 봄
- 각 에셋마다 인증 준비율이 보임

### 15.4 4순위: 구매자 검증 리포트

작업:

- 구매자가 인증서 또는 URL을 입력하면 리포트 형태로 결과 표시
- 기술적 상태보다 비즈니스 의사결정 문구 우선

완료 기준:

- “사용 가능”, “추가 승인 필요”, “위험”, “사용 불가”가 명확히 구분됨
- 다음 행동 CTA가 항상 표시됨

### 15.5 5순위: 실제 저장소/로그인/권한

작업:

- Supabase auth 연결
- Google login 활성화
- DB schema/migration 추가
- 역할별 접근 제어
- 파일 업로드 스토리지 연결

완료 기준:

- 사용자가 다시 로그인해도 작업 내용이 남아 있음
- 판매자와 구매자가 서로의 내부 정보를 볼 수 없음

## 16. 현재 단계에서 외부 제품 사용 방침

수익이 없는 현재 단계에서는 직접 모든 인프라를 만들면 안 됩니다. 직접 구현은 인증 로직과 UX에 집중하고, 범용 기능은 검증된 제품을 써야 합니다.

권장:

- 로그인: Google Login + Supabase Auth
- DB: Supabase Postgres
- 파일 저장소: Cloudflare R2 또는 Supabase Storage
- 배포: Vercel
- 이메일: Resend 또는 Postmark
- 한국 결제: Toss Payments 또는 PortOne
- 글로벌 결제: Stripe
- 고객지원: Crisp, Intercom, 또는 초기에는 Google Workspace 메일 + Notion/Linear 수동 관리

현재 실제 결제는 법인/개인사업자, PG 심사, 약관 확정 전까지 제한하는 것이 맞습니다. 데모에서는 “결제 예약”, “수동 인보이스”, “테스트 결제”로 처리하는 편이 안전합니다.
